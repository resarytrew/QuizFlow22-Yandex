# AI quota reservation

The existing API intended a UTC-day count of `ai_rate_limits` rows with limits of 5 for free users and 200 for Pro. Concurrent requests previously counted before the upstream call and inserted afterwards, allowing all of them through. In addition, the cleanup function removed rows after two hours, so the count could not enforce the intended daily window.

The proxy now takes a PostgreSQL transaction-scoped advisory lock for the user, reads the clock after obtaining the lock, counts the UTC-day entries, and inserts a uniquely identified reservation before contacting the upstream. The transaction is committed before the network call. A failed or rejected upstream call deletes its own reservation. Success retains it. No schema migration or new credentials are required. The insertion supports the canonical schema and the historical variant with a `feature` column. Cleanup retains entries for 48 hours so it cannot erase the current day's quota. Plan names and numeric limits remain unchanged; users who previously exceeded the intended daily limit because of early cleanup may now encounter the existing limit sooner.

Rollout: deploy the cleanup change before or together with the AI proxy, and ensure all active proxy instances use the new code; old instances do not take the advisory lock. deploying only the proxy while old cleanup runs still loses current-day records. Roll back by redeploying the previous functions. Rolling back restores both the concurrency and early-deletion defects. No historic rows can be reconstructed once the previous cleanup has deleted them.

A process killed after reservation but before cleanup can leave a slot consumed until the UTC day ends. A failed delete is logged and likewise fails closed; a transient quota denial can occur while a concurrent failure is being compensated. There is no request idempotency contract in the existing API, so retries after a successful upstream call are independent requests. No upstream API or plan logic was added.

Unit tests mock the database and upstream. For actual PostgreSQL locking, provision an isolated database named `quizflow_ai_quota_test` and set `PG_HOST`, `PG_PORT`, `PG_USER`, `PG_PASSWORD`, `PG_DATABASE=quizflow_ai_quota_test` and appropriate TLS configuration, then run `npm --prefix yc-functions run test:ai-quota:integration`. **The integration test drops and recreates the public schema in that exact database**; never point it at a database containing data. It exercises 20 concurrent reservations and a UTC-day boundary. It cannot establish production deployment or external infrastructure configuration.
